## 1. Library surface added this session

All display-related, all gated, none of it costing an existing consumer anything.

### Transport

```cpp
TxTicket enqueueExternal(uint16_t funcId, const uint8_t* data, uint16_t len, TxOptions = {});
TxTicket enqueueSplit(uint16_t funcId, const uint8_t* prefix, uint8_t prefixLen,
                      const uint8_t* body, uint16_t bodyLen, TxOptions = {});
```

`AFFA_MAX_PAYLOAD` **stays at 113**. Raising it to hold a 304-byte screen would widen the
inline buffer in every queue slot plus `finishJob()`'s stack copy — ~1.1 kB paid by everyone.
`enqueueExternal` borrows the caller's pointer (~48 B total); `enqueueSplit` copies a short
prefix and borrows a long body as one message, which is what a bitmap screen actually is.

Both refuse a `RenderSlot` and `reassertAfterSession`. **The refusal keys on `RenderSlot`,
not `TxOptions::coalesce`** — that flag defaults to `true` and testing it rejects every
ordinary call.

### Carminat

```cpp
Result showNavBitmap(const uint8_t* bitmap);         // 288 B, BORROWED until the ticket completes
Result navTick(bool phase);                          // 25 00 00 00 / 25 00 03 00 — UNCONFIRMED
Result showMenuN(uint8_t* scratch, uint16_t cap, const char* title,
                 const char* const* items, uint8_t count,
                 uint8_t firstVisible = 0, uint8_t selected = 0, uint8_t scrollMask = 0);
Result selectMenuItem(uint8_t index);                // 29 01 <index> — 8 bytes, no redraw
Result setTextStyled(const char* t, uint8_t icon, uint8_t srcIcon, uint8_t fmt);
static constexpr uint16_t menuScreenBytes(uint8_t count);
```

### Base

```cpp
RenderSlot lastRendered()   const;   // the last SCREEN the panel ACKed
uint32_t   lastRenderedMs() const;   // and when; both cleared on session loss
```

**This is the one to know about.** An application with both a scrolling line and a menu will
repaint over the menu a fraction of a second after the user opens it unless something
suppresses the repaint. `lastRendered()` is set by the transmit path itself, so unlike a flag
the application keeps it cannot drift:

```cpp
if (display.lastRendered() == RenderSlot::Text) marquee.tick();
```

It **reports**; it does not decide. `RenderSlot::Control` is excluded — `setPower` is a
payload with a slot but it draws nothing. Overlays (`Popup`, `InfoPopup`) do not replace the
screen underneath, so an app that cares about both layers must track the overlay separately.

### Types

`affa::keyName(Key)`, `affa::edgeName(KeyEdge)`.
`carminat::kScreenNav`, `kNav*` geometry, `kNavHeader`, `kMenuItemStride`, `kMenuFixedBytes`,
`kMenuMaxItems`, `kButtonsNone/Ok/YesNo`, `kButtonLabelLen`, `kSelectModeBox/List`.

## 2. The console — `examples/17_mediascreen`

**One command route.** `GET /api/cmd?op=<name>&…` → `{"ok":bool,"op":string,"msg":string}`.
Every action goes through it; the header shows the result of every press. Twenty-three ops,
all verified returning `ok` against the live panel.

Other routes: `POST /api/bmp` (288 bytes of hex — too long for a query string),
`GET /api/img?n=`, `/api/state`, `/api/keys`, `/api/frames` (TSV), `/api/log`.

Six tabs: **Bitmap** (editor + stored images + device-drawn animations) · **Text** (main line
with optional scroll and the `0x77` icon/source/format bytes, clock, power, popup,
fullscreen) · **Menus** (2-row, N-item, info menu with per-row scroll, info popup, message
box) · **Keys** (what the library decoded off the stalk, live) · **Wire** (every frame,
exportable) · **Settings** (family, hold, OTA, diagnostics).

`GET /api/cmd?op=panic` stops everything from a bare address bar — no script, no JSON.

Settings persist in NVS so a reflash does not undo them.

## 3. The six bugs, and why each one matters

These cost most of the session. Every one is a class of mistake, not a typo.

1. **The pane never drew because the opening was never sent.** Counters were perfect —
   62/62 Ok, zero fail — and nothing appeared. `16_navlab` only ever rendered *after*
   replaying `52 09 00` → `54 01` → `54 03`. **A clean transmit counter says nothing about
   the glass.**

2. **A `(void)`-cast `setPower` logged "display ON" whether or not it was accepted.** A log
   line that prints regardless of the result is a comment with a timestamp. The wire tap that
   replaced it found the real answer in one look.

3. **The tap hid its own evidence.** 43 CFs + 43 flow controls per image at 4 fps flushed a
   40-slot ring ten times a second. Nav continuations are dropped by default now; the first
   frame of each transfer is always kept, because that is where the header is.

4. **One lost backslash killed the whole console.** `\n` became a real newline inside a JS
   string; a `SyntaxError` anywhere means the script never runs, so every button died at once
   while the HTML rendered perfectly. The page is a C++ raw string literal, so it compiles,
   links, flashes and serves. `tools/check_web_ui.js` catches this in a second — **run it.**

5. **`send()` was a `const` arrow while `call()` was a `function`.** Only the hoisted form is
   reachable from inline `onclick` here, so half the controls silently did nothing. Anything
   an inline handler calls is a `function` declaration now.

6. **`ERR_CONNECTION_REFUSED` was the console exhausting its own socket table.** Three
   parallel fetches every 1.2 s against seven `esp_http_server` sockets. The board was
   healthy throughout — curl got 200 five times running. Polling is chained now, one request
   outstanding, with an overlap guard.

Two more worth carrying:

* **A repaint is not free and not idempotent.** Identical images and identical text are no
  longer resent. A static logo costs one transfer and then nothing; duty falls from ~25% to 0.
* **`showNavBitmap` BORROWS its bytes.** Double-buffer, and skip rather than queue when the
  previous frame is still in flight — a backlog never drains.

## 4. Confirmed on glass

* the `0x1F1` pane renders a 48×48 monochrome bitmap, MSB-first, row-major
* it is an **independent layer** — the info menu draws with it, and the image can be replaced
  under an open popup
* `52 09 00` / `52 00 00` is display on/off, and nothing draws at all while off
* the panel **tracks six menu items and draws two**, scrolling the viewport itself
* an info-menu row shows **8 characters** (column ruler)
* **the confirm box is closed with `54 03`** — it is a mode `0x05` screen, the same family as
  the full window
* a 304-byte transfer is 44 CAN frames at BS=1, 47–64 ms; ~23% duty at 250 ms; ~5000
  consecutive transfers with zero failures

## 5. Open, ranked

1. **Walk the console against the glass.** Every op returns `ok`; this panel ACKs everything,
   so that proves the transport and nothing else. The interesting failure is *accepted but
   not drawn*.
2. **Press the stalk with the Keys tab open.** Never tested. Validates panel → `0x1C1` → the
   `03 89` guard → decode. If nothing appears, that is itself a finding — the joystick is on
   the panel, not the radio.
3. **The Yes/No confirm box.** `showConfirmBox` is a **one-button OK box** (`21 05 00 00 01
   49`, byte 4 is the count). The real form is `21 05 01 00 02 49` with two 6-byte labels,
   selection via `29 05 <index>`. Fully specified in `docs/OEM-CSV-CORPUS.md` §4 — a builder
   and a test, not research. **The last thing in the library that is demonstrably wrong
   rather than merely unknown.**
4. **The caption slot `[3..9]`.** The earlier negative was retracted: that test wrote
   `[4..10]`. Use `16_navlab` (it has the header editor), write `%ABCDEF`, and if it does not
   draw, sweep `[11]` with the caption non-blank — `0x01 → 0x12` is the value the OEM changes.
5. **Are bytes 12/13 real geometry** or is the pane a fixed 48×48 window? `16_navlab` sends
   any W×H.
6. **`navTick`** — in the library, never confirmed on glass.
7. **The real menu item ceiling.** `kMenuMaxItems` is 10 on purpose; six is the most ever
   captured.
