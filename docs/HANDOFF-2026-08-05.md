**The `0x1F1` channel is decoded, confirmed on glass, and in the library.** This session
turned a byte range nobody had ever written to into a second display layer with an API, and

## 1. What is CONFIRMED — it happened on the bench panel

### 1.1 `0x1F1` is a 48×48 monochrome bitmap, and it renders

The OEM head unit's 302-byte nav screen decodes as **a 14-byte header plus 288 bytes of
bitmap**: row-major, 6 bytes per row, MSB-first, bit 7 of byte 0 is the top-left pixel.

```
21 0B 00 | 25 41 42 43 44 45 46 | 00 | 01 | 30 30 | <288 bytes>
^^ ^^ ^^   "%  A  B  C  D  E  F"   ^^   ^^   ^^ ^^
|  |  |     caption slot [3..9]    |    |    48, 48 — the geometry
|  |  |                            |    +--- moves 0x01 -> 0x12 between captures
|  |  |                            +--- NUL terminator
|  |  +--- 0x00, unknown
|  +------ kScreenNav 0x0B — the screen TYPE
+--------- kCmdScreen 0x21 — the same command the menu and fullscreen use
```

`0x21` and `0x0B` were **not** a discovery: `CarminatConstants.h` already had
`kCmdScreen = 0x21` with a screen-type byte after it (`0x01` windowed, `0x05` fullscreen).
`0x1F1` opens `21 0B` because it is the same command family on a different id.

The decode came from `docs/captures/"aknowledge on on display.csv"`, which is **complete** —
44 frames, PCI `11` then `21..2F 20..2F 20..2B`, zero sequence gaps. The repo had it
labelled frame-lossy for months; that is true of the ESP32 capture, not of the bus-analyser
trace. Nobody had reassembled it.

### 1.2 It is an INDEPENDENT LAYER, not a screen mode

This is the finding that makes the channel worth anything:

* the **info menu draws WITH the bitmap** on one screen
* the image can be **replaced underneath an open popup** and is seen to change

So the pane is a persistent widget you set once and update, not a screen you switch to.
`17_mediascreen` is built entirely on this.

### 1.3 Timing, measured

| | |
|---|---|
| one image | 304 wire bytes = 44 CAN frames |
| flow control | the panel runs ISO-TP **BlockSize 1** — every CF is a round trip |
| transfer time | **47–54 ms** alone, **~64 ms** with a title interleaving on `0x151` |
| OEM's own rate | 105 ms per image; two nav images **478 ms apart with different pixels** |
| sustained | 141 frames, 141 ok, 0 fail, 23% bus duty at 250 ms, heap flat |

The OEM animates this channel. Animating it is not our invention.

### 1.4 `52 09 00` is display ON, `52 00 00` is OFF

Three "display off" captures send `52 00 00` and **nothing follows them at all** — no text,
no bitmap. The one "display on" capture sends `52 09 00` and the text and the nav screen
follow within 25 ms. 3/1 across the corpus.

### 1.5 The `0x77` text header is fully documented — by MeganeCAN

`MeganeCAN/src/display/Carminat/CarminatDisplay.cpp` documents every byte, and all six line
up with the capture's `77 09 55 FF 31 01`:

| byte | field | values |
|---|---|---|
| 0 | mode | `0x74` full window · `0x77` windowed. A `0x77` sent while the full window is up **freezes the main screen**; `151 02 54 03` closes it |
| 1 | rdsIcon | `0x45` AF-RDS · `0x55` none. **The capture has `0x09`, in neither list** |
| 2 | fixed | `0x55` always |
| 3 | sourceIcon | `0xDF` MANU · `0xFD` PRESET · `0xFF` none |
| 4 | format | `0x19`–`0x3F` radio (5 digits + `.` + 1) · `0x59`–`0x7F` plain ASCII |
| 5 | control | `0x01` |

Which decodes the capture: format `0x31` is radio style, so `"   1056 "` is **not the string
1056 — it is 105.6 FM with the point drawn between the digits.** Eight characters is the
field width, not a coincidence.

### 1.6 Field widths

* **info menu row: 8 characters.** The ruler `----+----1----+----2…` comes back as `----+---`.

### 1.7 The menu is a 6-item list in a 2-row viewport

The panel accepts `[6] = 0x80 | itemCount` with length `36 + 27×N` and **tracks all N items**
— select item 5 and item 5 comes into view. But **the glass still draws two rows.** The panel
does the scrolling; the application no longer has to maintain a sliding window.

## 2. What is in the library now

### 2.1 Transport

```cpp
TxTicket enqueueExternal(uint16_t funcId, const uint8_t* data, uint16_t len, TxOptions = {});
TxTicket enqueueSplit(uint16_t funcId, const uint8_t* prefix, uint8_t prefixLen,
                      const uint8_t* body, uint16_t bodyLen, TxOptions = {});
```

**`AFFA_MAX_PAYLOAD` stays at 113.** Raising it to hold a 304-byte screen would widen the
inline buffer in every one of `AFFA_TX_QUEUE_DEPTH` slots plus `finishJob()`'s stack copy —
about **1.1 kB paid by every consumer** for a message most will never send. Instead:

* `enqueueExternal` **borrows** the caller's pointer. ~48 bytes total across the queue.
* `enqueueSplit` **copies a short prefix** and **borrows a long body**, sent as one message.
  A bitmap screen is a few header bytes that change per call in front of hundreds of image
  bytes that live in flash and never do; copying both needs a buffer as big as the message,
  borrowing both forces the caller to keep the header alive. Splitting costs neither.

`TxJob` gained `prefixLen`: bytes `[0, prefixLen)` come from the inline buffer, the rest from
`ext`. Every non-split job leaves one half empty, so this is the ordinary path plus one
predictable branch. `len`/`sent` widened to 16-bit — 302 does not fit a `uint8_t`, which is
what made a naive ceiling bump a non-starter.

Both refuse a `RenderSlot` and `reassertAfterSession`: both re-copy into storage the slot no
longer owns. **The refusal keys on `RenderSlot`, not `TxOptions::coalesce`** — that flag
defaults to `true` and testing it rejects every ordinary call.

### 2.2 Carminat

```cpp
Result showNavBitmap(const uint8_t* bitmap);        // 288 bytes, BORROWED until the ticket completes
Result navTick(bool phase);                          // 25 00 00 00 / 25 00 03 00 — UNCONFIRMED
Result showMenuN(uint8_t* scratch, uint16_t cap, const char* title,
                 const char* const* items, uint8_t count,
                 uint8_t firstVisible = 0, uint8_t selected = 0, uint8_t scrollMask = 0);
Result selectMenuItem(uint8_t index);                // 29 01 <index> — 8 bytes, no redraw
static constexpr uint16_t menuScreenBytes(uint8_t count);
```

Gates: `AFFA_ENABLE_NAV`, `AFFA_ENABLE_BIGMENU`, both default 1.
Constants: `kScreenNav`, `kNavWidth/Height/Stride/BitmapBytes`, `kNavHeader`,
`kMenuItemStride`, `kMenuFixedBytes`, `kMenuMaxItems`.

**`kMenuMaxItems` is 10, not 6, on purpose.** Six is the most ever *captured*, not a known
ceiling, and finding the real one needs a builder that can exceed it.

## 3. How to wire it into a real app

**Copy `examples/17_mediascreen`.** It is the pattern, not a demo.

```cpp
// 1. The image is BORROWED. Two buffers, and only ever draw into the idle one.
uint8_t frame[2][288];
uint8_t drawInto = 0;
volatile bool navBusy = false;
affa::TxTicket navTicket;

void pushFrame() {
  if (navBusy) return;                     // still in flight — SKIP, never queue up
  render(frame[drawInto]);
  if (display.showNavBitmap(frame[drawInto]) != affa::Result::Ok) return;
  navTicket = display.lastEnqueued();      // this is how you name the ticket
  navBusy   = true;
  drawInto ^= 1;
}

void onDone(affa::TxTicket t, affa::Result r, void*) {
  if (t == navTicket) navBusy = false;     // the ONLY place that knows the bytes are free
}
```

Rules that are not optional:

1. **Never overwrite a buffer that is in flight.** `showNavBitmap` borrows. Double-buffer, or
   gate on a busy flag cleared in `onComplete`. A single buffer tears the image on the wire.
2. **Skip, do not queue.** If the previous frame has not completed, drop this one. Queueing
   builds a backlog that never drains and the pane falls behind reality.
3. **Budget the bus.** 44 frames at BS=1 is ~50–65 ms. 250 ms is 23% duty and leaves room for
   text; 120 ms is the floor. Count dropped frames and show the number — it is the honest
   signal that the period is too short.
4. **The two layers do not contend.** The image goes out on `0x1F1`, text on `0x151`; give
   them separate timers so the title does not stutter when the pane is busy.
5. **Draw on the device** if anything is live. A clock that advances and a bar that fills are
   not knowable at build time. 288 bytes of RAM and a 5×7 font is the whole cost —
   `examples/17_mediascreen/media_render.h` is reusable as-is.
6. **`setPower(true)` before anything is drawn**, or the panel ACKs a screen it never lights.

## 5. RETRACTED — three things claimed this session that were wrong

### 5.1 "Bytes 4–10 as text does not work"

**The test wrote the wrong bytes.** The caption is `[3..9]`, seven bytes, and `0x25` is `'%'`
— its *first character*, not a separate unknown field, with `[10]` the terminator. The console
was writing `[4..10]`: it left `'%'` in place and shifted every character one position.

**Whether the caption renders is OPEN, not answered.** This is the first thing to re-test.

### 5.2 "The panel takes at least six rows"

It takes six **items** and draws two **rows**. The glass is a two-row viewport; that is a
property of the panel, not of the payload. What six items buy is panel-side scrolling
(§1.7), which is worth having and is not the same claim.

### 5.3 "`[11]` is a format or bit-depth byte"

It moves `0x01` → `0x12` between two nav captures, so it is not fixed. Unknown.

## 6. Open, ranked

1. **The caption slot `[3..9]`.** Re-test with the corrected span. If it still does not draw,
   sweep `[11]` (`0x01` → `0x12` is the value the OEM changes) with the caption non-blank —
   that pairing is the most likely unlock.
2. **Are bytes 12/13 real geometry?** `16_navlab` sends any W×H with the byte count following
   (`stride = ceil(W/8)`). Either the panel honours it or the pane is a fixed 48×48 window;
   both answers are useful.
3. **The Yes/No confirm box.** `21 05 01 00 02 49` with two 6-byte labels and `29 05 <index>`
   for selection. `showConfirmBox()` today emits `21 05 00 00 01 49` — a **one-button OK box**.
   The library has no path to the two-button form.
4. **`navTick`.** In the library, unconfirmed on glass. `25 00 00 00` / `25 00 03 00`
   alternating at 820 ms with nothing else on the bus; reads as a blink.
5. **The real item ceiling.** `/api/menusweep` walks 1→10.
6. **`B3 52 00×16`.** One sample, between the route-calc screen and the first bitmap.
